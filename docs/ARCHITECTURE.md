# KAEVR-AI Architecture

## Project Overview

KAEVR-AI is an evidence-first AI-powered cybersecurity platform designed to ingest security telemetry, detect threats, calculate explainable risk, coordinate AI-driven investigation and response, and present security incidents through a real-time SOC dashboard.

The project is divided into four primary modules, with each team member responsible for one module.

## Module 1 — Ingestion & Log Intelligence

### Purpose

Module 1 is responsible for collecting, parsing, validating, and normalizing incoming security logs and events before they are passed to the detection system.

### Responsibilities

- Receive security logs and events from supported sources.
- Parse raw security logs.
- Convert different log formats into a common schema.
- Validate required event fields.
- Prepare normalized events for downstream processing.
- Publish normalized events for Module 2.
- Store or index event data where required.

### Output

Module 1 produces a standardized `NormalizedEvent`.

The exact structure of the event exchanged between Module 1 and Module 2 will be defined in:

`docs/CONTRACT.md`

## Module 2 — Detection & Risk Engine

### Purpose

Module 2 analyzes normalized security events to detect suspicious activity, identify known threats, calculate risk, generate evidence-backed explanations, and map attacks to the MITRE ATT&CK framework.

### Responsibilities

- Detect suspicious activity using Sigma-style detection rules.
- Perform IOC matching for malicious IP addresses, domains, URLs, and file hashes.
- Perform ML-based behavioural risk analysis.
- Generate explainable risk factors.
- Calculate a final risk score.
- Link every important risk factor to supporting evidence.
- Map detected behaviour to MITRE ATT&CK techniques.
- Generate structured security alerts.
- Publish alerts for Module 3.

### Detection Pipeline

```text
              Normalized Event
                     |
          +----------+----------+
          |                     |
          v                     v
   Sigma Detection         IOC Matching
          |                     |
          +----------+----------+
                     |
                     v
              ML Risk Analysis
                     |
                     v
               Explainability
                     |
                     v
               Risk Aggregator
                     |
                     v
            MITRE ATT&CK Mapping
                     |
                     v
              Structured Alert
```

### Evidence-First Principle

KAEVR-AI follows an evidence-first approach.

A high risk score should not be generated without explaining why the event or incident is considered dangerous.

Each generated risk factor should be traceable to supporting security evidence.

For example:

```text
Encoded PowerShell detected
        |
        +--> Evidence Event: event-123

Known malicious IP contacted
        |
        +--> Evidence Event: event-123

Abnormal process behaviour
        |
        +--> Evidence Event: event-456
```

This allows analysts and downstream AI agents to understand why an alert was generated instead of receiving only a numerical risk score.

The exact alert schema will be defined in:

`docs/CONTRACT.md`

## Module 3 — Supervisor AI & Response

### Purpose

Module 3 acts as the reasoning and coordination layer of KAEVR-AI.

It consumes alerts generated by Module 2, investigates incidents, correlates evidence, coordinates AI capabilities, and recommends appropriate security responses.

### Responsibilities

- Consume security alerts from Module 2.
- Correlate related alerts and security events.
- Coordinate investigation workflows.
- Reconstruct attack timelines.
- Analyze available evidence.
- Determine incident context and severity.
- Generate response recommendations.
- Support AI Security Chat.
- Generate structured incident reports.

### Supervisor Flow

```text
Security Alert
      |
      v
Supervisor AI
      |
      +----------------------+
      |                      |
      v                      v
Investigation          Attack Timeline
      |                      |
      +----------+-----------+
                 |
                 v
          Decision / Context
                 |
        +--------+---------+
        |                  |
        v                  v
Response Agent       Incident Report
```

### Response Capabilities

The system may recommend or simulate actions such as:

- Blocking a malicious IP address.
- Terminating a suspicious session.
- Applying API rate limiting.
- Isolating a compromised account or endpoint.
- Escalating an incident for human investigation.
- Requesting additional evidence.

Real destructive actions should require explicit authorization unless the team later defines a safe execution policy.

---

## Module 4 — SOC Dashboard & Analytics

### Purpose

Module 4 provides the user-facing Security Operations Center interface for monitoring alerts, incidents, investigations, risk, threat intelligence, and system analytics.

### Responsibilities

- Display real-time security alerts.
- Display incidents and investigation status.
- Visualize risk scores and severity.
- Display alert evidence and explanations.
- Display MITRE ATT&CK mappings.
- Show reconstructed attack timelines.
- Display threat intelligence information.
- Provide security analytics and SOC KPIs.
- Show real-time notifications.
- Provide access to AI Security Chat.
- Display or download generated incident reports.

## Inter-Module Communication

The four modules must communicate using clearly defined shared contracts.

```text
Module 1
   |
   | NormalizedEvent
   v
Module 2
   |
   | Alert
   v
Module 3
   |
   | Incident / Decision
   v
Module 4
```

The exact field names, schemas, required fields, and message formats will be maintained in:

`docs/CONTRACT.md`

No module should silently change a shared contract.

Any contract change should first be communicated to the team because downstream modules may depend on the existing schema.

---

## Shared Infrastructure

The current planned shared infrastructure includes:

- Redpanda for real-time event streaming.
- OpenSearch for searchable security events, alerts, and related data.
- FastAPI for backend APIs and service endpoints.
- Python for backend security, AI, and detection services.
- Docker and Docker Compose for local service orchestration.
- A web frontend for the SOC dashboard.

The exact infrastructure configuration may evolve during implementation while the core module boundaries remain stable.
